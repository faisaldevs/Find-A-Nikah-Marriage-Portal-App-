**Audience:** the engineer / AI who owns the Find A Nikah backend.
**Written:** 2026-11-14 by the mobile (Flutter) side.
**Status of the app:** the whole Feed UI is built and runs on **dummy data**. No Feed endpoint is called yet. Nothing here blocks the app today — it is the contract we need to replace the dummy data.

## How to read this

- Each item has **Today** (what the app does), **Need** (the endpoint / answer) and **Why**. `P0` = blocks the phase, `P1` = wrong in an edge case, `P2` = nice to have.
- Please answer in this file or in a reply using the same § numbers.
- **We also ask you for one more document** (see §20): `FEED_MOBILE_IMPLEMENTATION_PLAN.md`, like the one you wrote for Marriage. It lets us build against your real behaviour instead of guessing.

## Product decisions already made (do not need an answer)

1. **No anonymous posts.** Every post, comment and like belongs to a real member. (Mobile has removed the toggle.)
2. **Same users as Marriage.** One account, one identity; Feed shows a *Feed profile* with a way to open the *Marriage profile* (§13).
3. **Names on Feed:** first name + last initial (e.g. `Ayat N.`) — the full name is never sent to Feed screens.
4. **Handle:** a visible `@handle` is shown, **auto-generated by the server** (member does not choose). The app uses `userId` as the identity everywhere; `handle` is a label only.
5. **Topics are fixed** (managed by admins); posts are filed under exactly one topic. **Groups (joinable communities) are not in v1.**
6. **Comments:** anyone who can see the post can comment and reply. **No gender separation.**
7. **Block** on Feed uses the **same block list** as Marriage and Chat.
8. **Own posts and comments can be edited and deleted.** Edit time limit: not decided — see §7.
9. **Text only in v1.** Media (photos / video / GIF) later.
10. **Out of v1:** notifications, moderation tooling (admin queue, auto-hide, profanity filter), saved posts, groups. The app keeps their buttons as "coming soon".

## Conventions we ask you to follow everywhere (P0)

### §1. Response shape, ids, paging, time, errors

- **Ids:** opaque strings. Every member is identified by `userId` (never by handle).
- **Paging:** `GET …?cursor=<opaque>&limit=<n>` → `{ items: [...], nextCursor: string|null, hasMore: bool }` — same as Marriage cards. Default `limit` 20, max 50.
- **Time:** ISO-8601 UTC (`createdAt`, `editedAt`). We format "9h ago" on the device; please do **not** send pre-formatted strings.
- **Counts:** integers. Please confirm counts are consistent with what the list shows (e.g. a deleted comment lowers `commentCount`).
- **Errors:** `4xx/5xx` with `{ code, message }` and **stable `code`s** (e.g. `POST_NOT_FOUND`, `POST_DELETED`, `NOT_ALLOWED`, `BLOCKED`, `EDIT_WINDOW_EXPIRED`, `RATE_LIMITED`, `VALIDATION_FAILED`). The app maps codes to behaviour (drop the item, show copy), not to message text.
- **Idempotency:** `like` / `unlike` / `follow` / `unfollow` / `save` must be idempotent (a repeat returns `200` with the current state, not `409`), because the app retries and can double-fire after a reconnect.

### §2. The author object (used in posts, comments, profiles)

```json
{
  "userId": "…",
  "displayName": "Ayat N.",
  "handle": "ayat_n4821",
  "photoUrl": "https://…",
  "countryCode": "bd",
  "isVerified": true,
  "isMe": false
}
```

- **Need:** confirm fields. `countryCode` lower-case ISO 3166-1 alpha-2 (picks the flag badge). `isMe` so the app never offers "Follow / Message / Block yourself".
- **Need:** which photo is used — the member's main profile photo? If the member has no approved photo, what is `photoUrl`? (`null` → the app draws a default avatar.)
- **Need:** what happens to the author object when the member **deletes their account, is deactivated, or blocked us**? We suggest `displayName: "Deleted member"`, no photo, no handle, and the post/comment kept or removed — please state which.
- **Why:** these are the fields every Feed card draws.

- **Need:** `GET /v1/me/feed-author` → the author object above for the signed-in member (`isMe: true`) plus `{ handle }`. Please confirm this works for **every** completed account without an extra setup step (handle is auto-generated at first call or at signup).

- **Need:** may a post be filed under *any* topic, or are some read-only (e.g. admin announcements)? Add `canPost: bool` per topic if so.
- **Why:** filter chips and the compose "Select topic" picker.

## PHASE 1 — read-only feed

### §5. Posts list (P0)

- **Today:** `fetchPosts(filter)` returns a flat list (no paging). Filter = *For you*, *New* or one topic.
- **Need:** `GET /v1/feed/posts?mode=forYou|new&topicId=&cursor=&limit=` → paged posts.
  - `mode=forYou` (default) — **please describe the ranking** (recency + engagement? follows? topics?). Is it stable across pages (the same post must not appear twice when paging)?
  - `mode=new` — strictly newest first.
  - `topicId` filters one topic (combined with either mode?).
- **Post object:**

```json
{
  "id": "…",
  "author": { …§2… },
  "topic": { "id": "…", "name": "All things marriage" },
  "body": "…",
  "createdAt": "2026-11-14T08:00:00Z",
  "editedAt": null,
  "likeCount": 3,
  "commentCount": 6,
  "viewCount": 412,
  "likedByMe": false,
  "isMine": false,
  "topComment": null
}
```

- **Need — visibility rules:** posts from members who **blocked me / I blocked / are muted / are deactivated** must be excluded — please confirm the server filters them (the app will not).
- **Need:** `body` maximum length (we show "read more" after 4 lines) and whether `body` can contain line breaks / links / mentions (`@handle`)? Plain text only, we assume.
- **Why:** the main screen. `likedByMe` gives the filled heart; `isMine` switches the post menu to Edit / Delete.

### §6. One post, by id (P0)

- **Today:** the post screen receives the whole post object from the list. That **crashes** when opened any other way (share link, app restored after the OS killed it). We are changing the screen to open **by id**.
- **Need:** `GET /v1/feed/posts/{postId}` → one post object (same shape as §5), or `404 POST_NOT_FOUND` / `410 POST_DELETED` / `403 BLOCKED`.
- **Why:** deep links, share links, and refreshing a post after returning from the comments.

### §7. Comments list (P0)

- **Today:** comments are 1 level of replies, sort *Most popular* / *Most recent*. The UI shows a comment, its author tag ("Author" pink badge on the post writer's comments), "Edited", like count, reply count and the replies inline; a "More comments" row exists.
- **Need:** `GET /v1/feed/posts/{postId}/comments?sort=popular|recent&cursor=&limit=` → paged **top-level comments**, each with the first N replies inline.
  `GET /v1/feed/comments/{commentId}/replies?cursor=&limit=` → the rest of a comment's replies.
- **Comment object:**

```json
{
  "id": "…",
  "postId": "…",
  "parentId": null,
  "author": { …§2… },
  "body": "Tea always wins.",
  "mention": { "userId": "…", "handle": "khalil_k2210" },
  "createdAt": "…",
  "editedAt": null,
  "isPostAuthor": false,
  "likeCount": 1,
  "replyCount": 1,
  "likedByMe": false,
  "isMine": false,
  "replies": []
}
```

- **Need:** how many replies are inlined per comment (we assume 2–3)? Is nesting **exactly one level** (a reply to a reply becomes a reply to the parent with a `mention`)? That is how the UI is drawn.
- **Need:** *Most popular* — formula (likes? likes + replies?). Stable paging for it?
- **Why:** the post screen.

## PHASE 2 — create, like, edit, delete posts

### §8. Create a post (P0)

- **Need:** `POST /v1/feed/posts` `{ topicId, body }` → the created post (§5 shape). No `anonymous` field.
- **Need — rules:** min / max `body` length, whether leading/trailing whitespace is trimmed, rate limit (posts per hour/day) and its error `code` (`RATE_LIMITED` with `retryAfterSeconds`).
- **Why:** the compose screen; the new post is inserted at the top of the feed immediately.

### §9. Like / unlike a post (P0)

- **Need:** `PUT /v1/feed/posts/{postId}/like` and `DELETE /v1/feed/posts/{postId}/like`, both idempotent, both returning `{ liked: bool, likeCount: int }`.
- **Why:** optimistic heart: the app flips it at once and rolls back on error; the returned count corrects any drift.

### §10. Edit and delete my post (P0/P1)

- **Need:** `PATCH /v1/feed/posts/{postId}` `{ body }` (topic changeable? we assume **no**) → the updated post with `editedAt`.
  `DELETE /v1/feed/posts/{postId}` → `204`.
- **Need — edit time limit:** **not decided on our side — please propose.** Options we see: unlimited, 15 min, 24 h. Unlimited edits let someone change a post under existing replies, so many apps cap it or show "Edited". State the limit and the error `code` (`EDIT_WINDOW_EXPIRED`).
- **Need:** what deleting a post does to its comments, likes and counts (hard delete? tombstone "This post was deleted"?). The app treats `POST_DELETED` as "remove it from the list".
- **Why:** own-post menu (Edit / Delete) and the "Edited" label.

### §11. Views (P2)

- **Today:** posts show a view count (`viewCount`). Dummy only.
- **Need:** how is it counted — server-side on `GET post`, or does the app report impressions? If the app must report, give us `POST /v1/feed/posts/views` `{ postIds: [...] }` (batched). We would rather **not** report per impression; tell us what you prefer.
- **Why:** the chart icon next to the share icon.

## PHASE 3 — comments and replies

### §12. Write, edit, delete, like comments (P0)

- **Need:**
  - `POST /v1/feed/posts/{postId}/comments` `{ body, parentId?, mentionUserId? }` → the created comment (reply when `parentId` is set).
  - `PATCH /v1/feed/comments/{commentId}` `{ body }` → updated comment (`editedAt`).
  - `DELETE /v1/feed/comments/{commentId}` → `204`. What happens to its replies?
  - `PUT` / `DELETE /v1/feed/comments/{commentId}/like` → `{ liked, likeCount }` (idempotent).
- **Need — rules:** comment length limits, rate limit, edit window (same as §10?), and who can comment on a post when the author **blocked** the commenter (`403 BLOCKED`?).
- **Why:** the comment composer ("Add a comment") and the reply action.

## PHASE 4 — profiles, follow, search

### §13. Feed profile + Marriage profile on one page (P0 for this phase)

This is the main design decision, please read carefully.

- **Design:** one profile page for a member with a switch **"Feed activity | Marriage profile"**. Opening a member from Feed lands on *Feed activity*; opening from the Marriage deck / Explore / Chat lands on *Marriage profile*.
- **Feed activity** needs: author object, country name, joined month, `followersCount`, `followingCount`, `postsCount`, `commentsCount`, `likesCount` and the tabs *Posts*, *Comments*, *Likes*.
- **Marriage profile** side: the **same full profile Muzz-style card** other members already see in the Marriage deck / Edit-profile Preview (photos, intentions, faith, interests, bio, verified card).

**Access rule (important):** Today we want to **show whatever the viewer is allowed to see and blur the rest** with a message such as *"This profile isn't available to you"*. In future, unlocking the blurred part may be **paid**. So the server must decide, per viewer, what is visible:

- **Need:** the Marriage-profile response for a member **as seen by this viewer** includes an `access` object, for example
  `{ "level": "full" | "partial" | "locked", "reason": "BLOCKED | NOT_IN_FILTERS | NOT_ELIGIBLE | PREMIUM_REQUIRED", "unlockable": true|false, "lockedSections": ["photos", "intentions", …] }`.
- **Need — security (must):** locked data must be **withheld by the server** (null / omitted, and locked photos replaced with a **pre-blurred low-resolution image** or no URL). **The app must never receive the real data and blur it itself**, because that can be bypassed.
- **Need:** which combinations are locked today (e.g. viewer blocked by them, they are outside the viewer's filters, they are hidden / paused, same-gender rule if any). We need the list of `reason`s.
- **Need:** is viewing someone's marriage profile **from Feed** counted as a profile **view** (the "Visited you" feed in Explore)? We suggest **yes**, but please say.
- **Need:** `GET /v1/profiles/{userId}` (marriage card, as seen by viewer) — does it already carry the `access` info or do we call a new endpoint?

### §14. Feed profile endpoints (P0 for this phase)

- `GET /v1/feed/users/{userId}` → author object + `countryName`, `joinedAt`, `followersCount`, `followingCount`, `postsCount`, `commentsCount`, `likesCount`, `isFollowing`, `followsMe`.
- `GET /v1/feed/users/{userId}/posts?cursor&limit` → their posts (each with `topComment` preview).
- `GET /v1/feed/users/{userId}/comments?cursor&limit` → their comments, each with the post it was left on (`{ comment, post: { id, authorDisplayName, bodyPreview } }`).
- `GET /v1/feed/users/{userId}/likes?cursor&limit` → posts they liked. **Privacy question:** should likes be public? Please advise (many apps keep "Likes" private).
- **Why:** the profile page and its tabs.

### §15. Follow (P0 for this phase)

- `PUT` / `DELETE /v1/feed/users/{userId}/follow` → `{ following: bool, followersCount: int }`, idempotent.
- `GET /v1/feed/users/{userId}/followers` and `/following` — paged author lists (the counts in the header will be tappable later; P2).
- **Need:** can a member follow someone who blocked them (`403 BLOCKED`)? Does following create a Marriage "like"? (It must **not**.)
- **Why:** the Follow / Following button on profiles and post headers.

### §16. Search (P1)

- **Today:** feed search only filters the posts already on screen; profile search filters a member's loaded posts.
- **Need:** `GET /v1/feed/search?q=&type=posts|people&cursor&limit` and `GET /v1/feed/users/{userId}/search?q=&type=posts|comments`.
  Min query length, matching (prefix? full text?), and ranking.
- **Why:** the Feed top-bar search and the "search a member's posts / comments" screen.

## PHASE 5 — safety + reach

### §17. Report, block, mute, hide (P0 for this phase)

- **Report:** reuse `POST /v1/reports` — please confirm it accepts `targetType: "post" | "comment" | "feedUser"` and a `reason` list (give us the reasons and their `code`s). `409` on a duplicate (same as Marriage).
- **Block:** the existing block endpoint, same list as Marriage and Chat. Confirm that after blocking, the member's posts/comments disappear from every Feed response (§5, §7, §14) and that I disappear for them.
- **Mute posts from a member** (menu row "Mute posts from X"): `PUT` / `DELETE /v1/feed/users/{userId}/mute` — hides their posts from *my* feed, no notification to them. They can still follow me, etc.
- **Hide a single post** — not in the UI; ignore.
- **Why:** the post menu (Report, Block, Mute).

### §18. Share (P1)

- **Need:** a **public/universal link** format for a post and a profile — e.g. `https://findanikah.app/feed/post/{postId}` and `/feed/u/{userId}` — and what the link shows when the app is not installed (a landing page?). Does a link to a post expose it to people outside the app (SEO / preview)? We assume **no**.
- The app will open the link in-app (id-based route, §6).

### §19. Message the author (P1)

- **Today:** a "Message" button on a Feed profile. The app has Chat for matched members only.
- **Need:** can a member message a **non-matched** member from Feed? We assume **no** unless a match exists. If not, what should the button do: hidden, "like first", or open a compliment flow? Please advise, with the rule that decides it (this must be consistent with how Marriage compliments work).
